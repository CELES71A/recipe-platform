## 全量 HTTP、典型结果与计划

环境 Python 3.14.6、Python SQLite 3.54.0、Mac arm64；默认入口 app.main。每项顺序执行 3 次本地 HTTP 请求，下表为中位数；未清缓存，不代表冷启动、P95、并发或其他硬件。完整原始三个样本、整页 ID、精确核对摘要、EXPLAIN 见 [full_review.json](full_review.json)。

| 场景 | 食材 ID／页 | 候选数 | HTTP 中位数 ms |
|---|---|---:|---:|
| 常见 salt | `[21]`，1 | 190,464 | 670.891 |
| 常见 sugar | `[30]`，1 | 102,808 | 390.450 |
| 少见 haeo | `[70]`，1 | 1 | 1.390 |
| garlic＋salt＋sugar | `[9,21,30]`，1 | 261,295 | 1,034.578 |
| 同一多选翻页 | `[9,21,30]`，2 | 261,295 | 1,032.649 |
| 38 完全输入 | `[1,2,3,4]`，1 | 48,970 | 261.061 |
| 38 部分输入所在页 | `[1,2]`，18 | 17,958 | 113.370 |

每页 12 条。各输入用不同于实现的全关联聚合及 Fraction 对完整候选排序，核对 API total、页内 ID 顺序、两类食材明细和数量。全量中 38 需要 4 种，紧随其后的 32798 等只需 1 种，但均为 100% 时仍按 ID 升序，实际通过。重复输入完全一致；38 的详情仍为 4 种食材、9 步。

食材查找 `blue` 共 30、`salt` 共 93、`haeo` 共 1、字面 `%` 共 20；blue 第 2 页与独立目录切片一致。查询通常约 1–3 ms，具体三个样本见 JSON。

计划：候选使用 `idx_recipe_ingredients_ingredient`；按 recipe_id 读取所需和当前页明细使用关联主键索引；发布状态／食谱查找使用状态索引和整数主键。GROUP BY、DISTINCT 和完整排序有临时 B-tree。名称 `%关键词%` 为食材表扫描；7,309 种食材的实测如上。只为当前页一次批量读取食材名称，没有逐卡查询。

## 索引实验与限制

在另一份独立全量副本新增 `(ingredient_id,recipe_id)`、`(recipe_id,ingredient_id)` 两个覆盖索引，交替各测 3 次直接数据库调用，返回内容完全一致。见 [index_experiment.json](index_experiment.json)：

| 查询 | 原索引中位数 ms | 两覆盖索引 ms |
|---|---:|---:|
| salt | 676.881 | 464.307 |
| 多选 | 1,038.522 | 1,143.457 |
| 38 完全输入 | 260.854 | 168.417 |

由于多选反而退化，本次不引入该索引组合、不增加迁移、不删除 B 可能使用的现有索引。实验时间是直接数据库调用，不和上面的 HTTP 时间混作同一指标。多选约 1 秒仍是可进一步优化的场景，尚未测并发、P95、锁竞争或跨设备性能。
